# Validate Before Building

When someone says "we need this feature," the worst response is to spend four weeks building something only to hear "that's not what I meant." The goal is to figure out what they mean as fast as possible, with minimal effort.

## Fast-learning loops

- **Prototype in 1 hour** and show it. "No, that's not what I meant, you should change this part here" is a great outcome — you learned on day one.
- **Write a spec in 30 minutes** and walk through it. The spec surfaces misunderstandings before a line of code is written.
- **Ship one slice per day.** Each day what you built hits reality. On day two someone says "you know what, we should change…" — and you still have time.
- **Reduce scope to the unknown.** Skip the parts you're already sure about. Focus on the bits where you don't know yet — that's where learning is needed. Don't build five login methods if all you need to validate is one.
- **Fake a demo video.** Show it around and get input before building anything.
- **Write the press release.** Why spend a week building something if the idea can be captured in three paragraphs? If the write-up doesn't get people excited, the feature won't either.
- **Write the README example code.** Does the API in the readme look right? People don't need an SDK built if they dislike the API in the readme.
